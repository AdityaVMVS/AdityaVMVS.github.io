Your Device Is Too Slow: Should You Change the Hardware, Software, or Both?

A practical look at hardware, software, and the data movement between them, with clear examples of where performance is won or lost.

October 4, 2026 · 15 min read

Imagine you are working on a device and suddenly receive a new requirement:

“The system needs to run faster. Reduce the execution time.”

The first thought might be:

Do we need a faster CPU? More cores? A GPU? More memory?

Maybe.

But performance problems are rarely solved by simply adding faster hardware.

A system can be slow because of the hardware, the software, or because the software is not using the hardware efficiently. In many real products, some of the biggest performance improvements come from the third category: HW-SW optimization.

So before changing anything, the first question should be:

Where is the system actually spending its time?

Step 1: Find the Bottleneck

Suppose an application takes 100 ms to complete one operation.

Imagine the breakdown is:

Now imagine we replace the CPU with one that performs calculations twice as fast.

The 20 ms computation might fall to around 10 ms.

But the total execution time only changes from:

100 ms → 90 ms

We bought a faster processor, but the application improved by only about 10%.

Why?

Because the CPU was not the main problem.

This is known as Amdahl's Law: you can only speed up the part you improve.

This is why performance engineering should normally begin with profiling rather than hardware changes.

We need to determine whether the system is:

compute-bound, memory-bound, I/O-bound, communication-bound, or synchronization-bound.

Once we know that, we can decide where to optimize.

On a CPU, perf shows where the time goes. On a GPU, Nsight Systems does. On a microcontroller, a cycle counter does.

1. Hardware Optimization

The main focus of this blog is to discuss more on the SW, HW-SW optimization. There are many hardware-level techniques for improving performance, but let us briefly look at two simple techniques.

Pipelining

Instead of waiting for one instruction to completely finish before starting the next one, processors divide execution into stages.

For example:

Fetch → Decode → Execute → Memory → Write Back

Different instructions can occupy different stages simultaneously.

Think of it like an assembly line.

Without pipelining:

Item 1 finishes → Item 2 starts → Item 3 starts

With pipelining:

Item 1 → Item 2 → Item 3

are moving through different stages at the same time.

Pipelining therefore improves throughput, although it does not necessarily reduce the latency of one individual instruction.

More Parallel Hardware

Another solution is adding more hardware capable of working simultaneously.

This could mean:

more CPU cores, wider SIMD units, additional execution units, more memory channels, GPUs, AI accelerators, or dedicated hardware blocks.

Instead of processing:

A → B → C → D

we may be able to process:

A | B | C | D

simultaneously.

However, parallel hardware helps only when the workload itself contains enough parallelism.

Adding 64 cores to a program that is mostly sequential will not magically make it 64 times faster.

And this is where software becomes extremely important.

2. Software Optimization: Often the First Place to Look

Changing software is usually cheaper and easier than redesigning hardware.

More importantly, inefficient software can waste even extremely powerful hardware.

Start With the Algorithm

The largest software improvement often comes from doing less work, not doing the same work faster.

Suppose an algorithm processes N elements.

An inefficient implementation may require approximately:

N² operations

while a better algorithm may require:

N log N operations

For small inputs, the difference may not matter.

For millions of elements, it can completely dominate performance.

This is why optimizing a bad algorithm with threads, GPUs, or assembly code is often the wrong starting point.

First ask:

Can we reduce the amount of computation itself?

Memory Access Can Matter More Than Computation

Processors are extremely fast compared with main memory.

Because of this, a program can spend a surprising amount of time waiting for data.

For scale: an L1 cache hit takes about a nanosecond, while DRAM takes roughly 60 to 100 nanoseconds (rough figures that vary by system).

Consider accessing an array sequentially:

This is generally cache-friendly.

Now imagine accessing:

Same work, different orderC
// Sequential
for (size_t i = 0; i < N; i++) sum += A[i];

// Scattered (idx[] is a shuffled list of indices)
for (size_t i = 0; i < N; i++) sum += A[idx[i]];

The CPU may constantly fetch new cache lines from memory.

The calculations might be simple, but memory access becomes expensive.

This is why techniques such as locality, blocking and tiling are widely used.

Instead of processing a huge data structure randomly, software works on a smaller region that can remain inside the CPU cache.

Intel, for example, describes cache blocking as an important optimization because processors move data in cache lines and benefit when nearby data is reused before being evicted. [1]

Avoid Unnecessary Data Copies

Consider:

Source memoryCPU stagingTemporary bufferAnother bufferGPU memory

Each additional copy consumes time and bandwidth. Remove copies that the workload does not need.

If the system copies gigabytes of data repeatedly, those copies can become more expensive than the computation itself.

Better designs try to reuse buffers, operate in place when safe, use DMA when appropriate, keep data near the processor that needs it, and avoid repeatedly moving the same data between CPU and accelerator memory.

This becomes especially important when GPUs are involved.

NVIDIA specifically recommends minimizing transfers between CPU memory and GPU memory because host-to-device communication can be much slower than accessing memory already local to the GPU.

Sometimes performing a slightly slower calculation on the GPU can still make the whole application faster if it avoids copying the data back to the CPU.

That is an important HW-SW optimization principle:

Do not optimize one function in isolation. Optimize the complete data path.

Use Parallelism Carefully

Suppose you have 48 CPU cores.

Creating 48 threads sounds like the obvious solution.

But imagine all 48 threads continuously update the same shared variable.

Now they have to synchronize.

Locks, atomic operations, cache coherence traffic, and scheduling overhead can reduce the expected performance.

Sometimes:

16 well-designed threads

can outperform:

48 badly communicating threads.

Good parallel software tries to divide work so that each thread operates mostly on its own data and communicates only when necessary.

Vectorization

Modern CPUs can perform one instruction on multiple pieces of data using SIMD instructions.

Instead of conceptually doing:

one vector instruction may process several values together.

Compilers can automatically vectorize many loops, but programmers can help by keeping loops simple, using contiguous memory, reducing dependencies between iterations, and selecting data structures that are friendly to vector operations.

This is one reason performance-oriented software cares so much about how data is stored, not only about the algorithm operating on it.

3. The Interesting Part: HW-SW Optimization

This is where computer architecture becomes especially important.

Instead of asking:

“How do we make the hardware faster?”

or:

“How do we make the software faster?”

we ask:

How should software behave based on how the hardware is actually organized?

Consider the complete path:

CPU → Cache → Interconnect → Memory

and in heterogeneous systems:

CPU → Cache → DRAM → PCIe/Interconnect → GPU → GPU Memory

Every movement has a cost.

Cache Design: Two Caches for 48 Cores or 48 Caches?

Suppose we are designing a 48-core processor.

One extreme design might have only a few large caches shared by all 48 cores.

Another might give every core its own cache.

Which one is faster?

There is no universal answer.

Large Shared Cache

Imagine 48 cores sharing two large caches.

Sharing has advantages.

If Core 1 produces data that Core 2 needs, both may be able to access the shared cache.

There is also less duplication of the same data across many private caches.

But now 48 cores are competing for the same resource.

You can get:

contention → queueing → higher latency → reduced effective bandwidth

One workload can also occupy a large portion of the shared cache and interfere with another workload. Intel discusses this type of shared last-level-cache contention as a performance concern in multicore systems.

Private Cache Per Core

Now imagine every core has its own cache.

Core 0 accesses Cache 0.

Core 1 accesses Cache 1.

...

Core 47 accesses Cache 47.

Local accesses can now be extremely fast, and aggregate cache bandwidth can be much higher.

But another problem appears.

Suppose Core 0 changes variable X.

Core 1 has another cached copy of X.

How do we guarantee that Core 1 does not continue using the old value?

We need cache coherence.

Protocols such as MESI and related schemes track the ownership and validity of cache lines between cores.

As core count increases, coherence traffic can itself become expensive, especially when many cores frequently write shared cache lines.

That is why modern processors generally use a hierarchy rather than choosing one extreme.

A simplified architecture might look like this. Real processors vary: some share L2 within a core cluster.

The small caches provide low latency near the CPU cores.

The larger last-level cache improves sharing and provides another layer before expensive DRAM accesses.

Real processors use variations of this idea. For example, Intel processors have used private lower-level caches combined with a shared last-level cache.

Software Can Either Help or Destroy Cache Performance

Even with an excellent cache architecture, software can create unnecessary coherence traffic.

Suppose two threads each update their own counter:

False sharing and the fixC
struct Counters { long a; long b; };   // a and b likely share one cache line

struct Padded { alignas(64) long a; alignas(64) long b; };  // one line each

There appears to be no sharing.

But imagine A and B happen to occupy the same cache line.

Now every update can cause the cache line to move between cores.

This is called false sharing.

The variables are logically independent, but the hardware coherence system sees the entire cache line. Coherence keeps cached copies coordinated; threads still need appropriate synchronization when they share data.

Performance-oriented software can avoid this by separating frequently written variables, partitioning data between threads, aligning structures properly, and reducing shared writes.

This is a perfect example of why software developers benefit from understanding computer architecture.

Where Should Memory Be Placed?

Now suppose our 48-core machine has multiple memory controllers.

Not every core may be equally close to every piece of DRAM.

When memory access cost depends on where the core and memory are located, this is a NUMA, or Non-Uniform Memory Access, architecture.

Imagine:

A core in Group A accessing Memory A may get relatively low latency.

The same core accessing Memory B may require traffic across an interconnect.

So memory placement matters.

AMD's optimization guidance recommends keeping computation and its memory close together where possible. On Linux, memory allocation may follow a first-touch policy, meaning the NUMA location where data is first initialized can affect where the memory physically resides.

This gives us an important software optimization.

Instead of:

One thread initializes

Thread 0 initializes the entire array.

All pages tend toward one NUMA node

Other workers may need remote memory.

Workers initialize their parts

Each worker first touches its own region.

Part 0Part 1…

Pages are more likely to be near their consumers.

Placement is page-based and depends on memory policy, available capacity, and where each thread runs.

we may initialize different portions using the threads that will later process them.

Now data is more likely to be allocated closer to its consumer.

This can reduce remote-memory traffic and improve aggregate bandwidth.

CPU Optimization: Keep the CPU Fed

A CPU performs best when instructions and data arrive continuously.

A few common techniques are:

Thread affinity: Keep important threads on appropriate cores instead of constantly migrating them.

Cache-friendly layouts: Organize data so information used together is stored together.

Prefetching: Fetch data before the processor actually needs it.

Reduce branch unpredictability: Frequently mispredicted branches can flush useful work from the CPU pipeline.

Reduce synchronization: Locks and atomic variables can become serialization points.

An important principle is that adding CPU threads helps only until another resource becomes the bottleneck.

For example:

Once memory bandwidth is saturated, adding more cores does almost nothing.

The optimization target should now move from CPU parallelism to memory behavior.

GPU Optimization: Give the GPU the Right Kind of Work

GPUs are excellent at executing huge numbers of similar operations.

Suppose we need to process ten million pixels.

A CPU might divide them among a few dozen cores.

A GPU may execute thousands of lightweight threads.

But GPU performance depends heavily on how the software feeds it.

One of the most important techniques is coalesced memory access.

If neighboring GPU threads access neighboring memory locations, the GPU can combine those accesses into a smaller number of memory transactions. Scattered accesses can require many more transactions. NVIDIA identifies coalesced global-memory access as a high-priority CUDA optimization.

Similarly, GPU programs should try to reduce branch divergence, reuse data through fast on-chip/shared memory when appropriate, give the GPU enough parallel work, and avoid launching extremely small kernels repeatedly.

Another important technique is batching.

Instead of:

Send itemRun GPUReceive result

Repeat the transfer and launch sequence for every item.

use:

Send 1,000 itemsRun GPUReceive 1,000 results

A batch shares communication and launch overhead across more useful work.

The GPU performs more useful computation relative to communication and launch overhead.

CPU + GPU: Data Movement Can Decide Everything

Imagine a CPU performs one operation in:

10 ms

while a GPU performs it in:

2 ms.

GPU sounds like the obvious winner.

But suppose:

Total: 6 ms upload + 2 ms compute + 6 ms download =

14 ms

The CPU version is actually faster.

Now suppose we perform 20 operations on the same data while keeping it on the GPU:

Now the GPU may win by a large margin.

This is why deciding where computation happens and where data lives is just as important as choosing the fastest processor.

Bus and Interconnect Optimization

The CPU, GPU, memory and peripherals must communicate through buses and interconnects such as PCIe, memory buses and on-chip networks.

Sending thousands of tiny transfers can create significant overhead.

Instead of:

Many small requests
4 B4 B4 B4 B4 B4 B4 B4 B

Setup overhead repeats.

Combined transfer
One larger payload

Setup overhead is shared.

software can often combine data into larger transactions.

DMA can also allow devices to move data without requiring the CPU to manually handle every byte.

Data alignment matters as well. Intel's optimization guidance, for example, recommends properly aligned and appropriately sized PCIe transactions for maximizing PCIe bandwidth on applicable platforms.

Modern multicore SoCs also use sophisticated coherent interconnects so processors and accelerators can share data while maintaining a consistent view of memory. Hardware coherence can reduce software cache-maintenance overhead, although coherence itself consumes bandwidth and hardware resources.

Again, everything is a tradeoff.

Other Techniques Widely Used in Industry

Several additional optimizations appear repeatedly in high-performance systems.

Kernel fusion combines multiple GPU operations so intermediate data does not repeatedly travel to slower memory.

Mixed precision and quantization use smaller numerical formats such as FP16, BF16 or INT8 when the application can tolerate them. This is especially important in AI workloads because smaller data can mean more computation per cycle and less memory traffic.

Double buffering allows the system to process one buffer while the next buffer is being loaded.

For example:

Instead of waiting for each operation sequentially, communication and computation overlap. This requires suitable hardware and independent work; asynchronous APIs alone do not guarantee overlap.

Asynchronous execution uses the same idea. CPUs, GPUs, storage and network devices can work concurrently rather than making everything wait for everything else.

Profile-guided optimization and compiler optimization allow compilers to perform transformations such as inlining, vectorization, loop optimization and code layout using knowledge about real program behavior.

Specialized accelerators are another major trend. Instead of forcing the CPU to perform everything, modern systems contain hardware for graphics, AI, video encoding, cryptography, networking and signal processing.

The goal is not simply:

“Build a faster processor.”

The goal is:

Run each workload on the hardware architecture that executes it most efficiently.

The Bigger Picture

When someone says:

“Make the device faster.”

there are really three optimization layers.

Hardware

Improve what the machine is physically capable of doing.

Examples include pipelining, parallel execution units, wider SIMD, more memory channels and specialized accelerators.

Software

Reduce unnecessary work and make better use of the available hardware.

Choose better algorithms, improve locality, parallelize carefully, vectorize, reduce copies, reduce synchronization and batch operations.

Hardware + Software

Understand the architecture and organize software around it.

Place data near the processor using it.

Keep hot data in cache.

Avoid unnecessary cache coherence traffic.

Keep CPU threads close to their memory.

Feed GPU threads contiguous data.

Avoid repeatedly transferring CPU/GPU data.

Batch bus transactions.

Use the right processor for each stage.

So Where Should You Optimize First?

The answer is not automatically hardware or software.

Start by measuring the system.

Use the profile to find the biggest delay, then choose a targeted change. This sheet shows where to look and what to try.

After each change

Check correctness, compare end-to-end time, and profile again. Use the same workload and change one thing at a time. Fixing one bottleneck may expose another.

One of the most useful lessons in computer architecture is this:

Performance is not only about how fast you can compute. It is also about how little data you move, how close that data is to the compute unit, and how much useful work can happen in parallel.

A powerful CPU running poorly structured software can be slow.

A powerful GPU constantly waiting for PCIe transfers can be slow.

Forty-eight cores fighting over shared cache lines can be slower than a smaller number of well-utilized cores.

The fastest system is usually the one in which hardware architecture and software behavior are designed to work together.
