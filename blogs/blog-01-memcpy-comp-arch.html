What a memcpy( ) Interview Question Taught Me About Computer Architecture

A single interview question about optimizing memcpy() sent me from software tricks to RISC-V pipelines, hazards, and hand-tuned assembly, and taught me exactly where hardware draws the line on how fast code can go.

September 20, 2026 · 9 min read

The question that started it

Have you ever stopped to think about what actually happens underneath the hundreds of lines we write every day? Even something as ordinary as a for loop hides a whole machine's worth of work. Most of the time, the abstraction does its job and we never need to look beneath it. Then one question suddenly makes that entire layer visible.

Mine came in an interview. The question was simple: how would you optimize a memcpy() function? Coming from a firmware background, I first thought about software-level techniques: reducing unnecessary function-call overhead, avoiding repeated work inside the loop, helping the compiler optimize more aggressively, and improving how the pointers are accessed. All reasonable ideas.

Then the interviewer pointed directly at the loop. Can you reduce the number of loop iterations below n?

My first reaction was: if I need to copy n bytes, don't I have to perform n copies? That was the key distinction. The goal was not to copy less data. It was to copy more data during each iteration.

From n iterations to n / 32

A straightforward memcpy implementation copies one byte at a time. I'm keeping the same void* interface as the standard library function:

Naive byte-by-byte copyC
#include <stddef.h>
#include <stdint.h>

void* myMemCpy(void* dest, const void* src, size_t n) {
    uint8_t* d = (uint8_t*)dest;
    const uint8_t* s = (const uint8_t*)src;

    for (size_t i = 0; i < n; i++) {
        d[i] = s[i];              // one byte per iteration
    }

    return dest;
}

The loop runs n times because every iteration moves exactly one byte. So the real optimization question becomes: what if one iteration represented 32 bytes of work instead of one?

One way to express that idea in C is to define a 32-byte block and copy complete blocks first:

32-byte block copyC
typedef struct {
    uint8_t data[32];
} Block32;

void* optimized_memcpy(void* dest, const void* src, size_t n) {
    uint8_t* d = (uint8_t*)dest;
    const uint8_t* s = (const uint8_t*)src;

    // Number of complete 32-byte blocks
    size_t blocks = n / 32;

    // Remaining bytes after those blocks
    size_t remainder = n % 32;

    Block32* d_block = (Block32*)d;
    const Block32* s_block = (const Block32*)s;

    // Main loop: copy 32 bytes per iteration
    for (size_t i = 0; i < blocks; i++) {
        d_block[i] = s_block[i];
    }

    // Move past the blocks already copied
    d += blocks * 32;
    s += blocks * 32;

    // Cleanup loop: copy the remaining 0 to 31 bytes
    for (size_t i = 0; i < remainder; i++) {
        d[i] = s[i];
    }

    return dest;
}

This is a simplified illustration of the block-copy idea rather than a production memcpy implementation, since arbitrary buffers introduce alignment, aliasing, and effective-type considerations in C.

This is the part that changed how I thought about the problem. The original main loop executes n times. The new main loop executes only n / 32 times, then a small cleanup loop handles n % 32 leftover bytes.

Example: copying 100 bytes

100 / 32 = 3 complete blocks and 100 % 32 = 4 remaining bytes.

So instead of making 100 passes through the main copy loop, the block loop runs only 3 times to move 96 bytes, followed by 4 byte-sized cleanup copies.

The main source-level change here is doing more work per loop iteration. In the original byte-by-byte version, copying 100 bytes requires 100 iterations. With 32-byte blocks, the main loop runs only 3 times to copy 96 bytes, followed by 4 cleanup iterations for the remaining bytes.

So at the source-code level, this example goes from 100 explicit loop iterations to just 7 total, with only 3 iterations doing the bulk of the work. That reduces loop-control overhead such as comparisons, increments, and branches.

But that made me curious about what was happening underneath. I had reduced the loop iterations at the C level, but could the efficiency be improved even further?

The processor does not execute C directly. The compiler translates that code into machine instructions, which raised the next question for me: can we optimize the assembly itself?

To answer that, I first needed to understand how those instructions move through the processor pipeline and where stalls or unnecessary overhead can appear.

Before touching assembly, I had to understand the pipeline

My first attempt was to just start writing assembly and guessing at improvements, but that did not go anywhere useful. Every idea I had, use fewer instructions here, reorder something there, only made sense if I knew how the processor actually executes instructions one after another. So before writing a single optimization, I went back to basics and looked at the pipeline.

A common educational RISC-V implementation uses the classic five-stage pipeline:

Inside the CPU: five pipeline stages
  1. IF: Instruction Fetch

    Fetch the next instruction from memory.

  2. ID: Instruction Decode

    Decode it and read the source registers it needs.

  3. EX: Execute

    Do the arithmetic, or compute a memory address.

  4. MEM: Memory Access

    Actually read from or write to memory, for loads and stores.

  5. WB: Write Back

    Write the result back into a register.

The pipeline is what makes it possible to overlap instructions. While one instruction is in EX, the next can already be in ID, and the one after that in IF. Throughput goes up because the stages stay busy at the same time instead of one instruction finishing completely before the next one even starts. Once I understood this, the goal for hand-written assembly became obvious: keep the pipeline full, and avoid anything that forces it to stall or throw work away.

Different instructions can sit in different stages at the same time, and that overlap is exactly what pipelining is for. But it also raises two practical questions for a loop like mine: once a value has been loaded, is it actually ready for the instruction that needs it next, and when the CPU hits a branch, which instruction should it fetch after that?

Data hazard. A data hazard happens when a later instruction needs a value that an earlier instruction has not finished producing yet. A general example makes this easy to see:

lw t0, 0(a1) followed by add t1, t0, t2

The add depends on t0, but the load has not actually delivered that value until later in the pipeline. Forwarding lets the CPU pass the value straight to the instruction that needs it instead of waiting for it to be written back to a register, and that removes the wait in most cases. Even so, a simple five-stage core can still need a one-cycle stall right before that dependent instruction runs. My own copy loop follows lw with sw rather than an add, and whether that specific pairing stalls comes down to how the particular core handles forwarding into a store.

Control hazard. A control hazard happens because the CPU has to decide what to fetch next before it actually knows how a branch will resolve. A loop-ending branch is a good general example:

bnez a2, copy_loop

On most passes through the loop, this branch is taken, and only on the final pass does execution fall through instead. On a core with dynamic branch prediction, the predictor can learn that pattern over repeated iterations, so a taken branch does not automatically cost a flush every time. What it can still get wrong is the exit itself, the one pass where the usual pattern breaks. I had originally assumed every taken branch in a loop was expensive by default, and that turned out to be an oversimplification.

With a clearer sense of both hazards, I went back to the copy loop to see what unrolling would actually change.

Trying to make memcpy faster in assembly itself

To reason about what the machine-level copy could look like, I started with the simplest case: a scalar word-copy loop on a 32-bit RISC-V core. Each lw/sw pair moves one 4-byte word, and eight such word copies make the same 32-byte block used in the C example.

For simplicity, assume the source and destination are suitably aligned for 32-bit word accesses. Here is roughly what that plain word-copy loop looks like:

Baseline word-copy loopRISC-V
copy_loop:
    lw   t0, 0(a1)      ; load word from src   (a1 = src pointer)
    sw   t0, 0(a0)      ; store word to dst    (a0 = dst pointer)
    addi a0, a0, 4      ; dst += 4
    addi a1, a1, 4      ; src += 4
    addi a2, a2, -1     ; words-- (a2 = remaining word count)
    bnez a2, copy_loop  ; loop while words != 0

Six instructions moving four bytes, repeated n/4 times. Once I knew what to look for, loop unrolling became interesting because it clearly reduces loop-control overhead and can also provide more scheduling room for the load/store sequence, depending on the core's forwarding paths.

Technique — unroll the loop to match the 32-byte block

Instead of loading one word and immediately storing it, unrolling lets the loop load several independent words first and then store them. Here, eight 4-byte words make one 32-byte block, matching the C example:

32-byte unrolled copy loopRISC-V
copy_loop:
    lw   t0,  0(a1)
    lw   t1,  4(a1)
    lw   t2,  8(a1)
    lw   t3, 12(a1)
    lw   t4, 16(a1)
    lw   t5, 20(a1)
    lw   t6, 24(a1)
    lw   a3, 28(a1)

    sw   t0,  0(a0)
    sw   t1,  4(a0)
    sw   t2,  8(a0)
    sw   t3, 12(a0)
    sw   t4, 16(a0)
    sw   t5, 20(a0)
    sw   t6, 24(a0)
    sw   a3, 28(a0)

    addi a0, a0, 32     ; dst += 32
    addi a1, a1, 32     ; src += 32
    addi a2, a2, -1     ; one 32-byte block completed
    bnez a2, copy_loop  ; a2 = remaining block count

This rewrite helps with both issues. The matching stores are separated from their loads by independent work, which can give the pipeline more room to resolve load-to-store dependencies on a core where that pairing would otherwise stall. At the same time, one loop pass now moves the same 32 bytes represented by one Block32 assignment in C, with a single branch and one set of pointer updates for the whole block. The C cleanup loop still handles any remaining n % 32 bytes.

Seeing it laid out this way is what turned "unroll your loops" from a rule of thumb into something I could actually reason about. It reduces loop-control overhead and can increase the spacing between related loads and stores, even though how much that translates into real speedup still depends on the specific core and its forwarding behavior.

Where this stops working

It would be easy to assume you can keep applying these ideas indefinitely and the loop just keeps getting faster. It does not, and the two reasons that matter most are hardware constraints that no amount of clever assembly gets around.

  • Scalar access width sets one limit. On base RV32I, ordinary integer loads and stores move at most 32 bits at a time. Moving more data per instruction requires wider ISA support, such as vector operations or other wider-access extensions, or multiple scalar instructions.
  • Loop unrolling has a turning point. Fewer branches helps, but unroll far enough and the loop body grows past what comfortably fits in the instruction cache, or it needs more live registers than the architecture actually has, forcing spills back to memory. At that point you have traded a control hazard for a memory access problem, which is a step backward, not further progress.

Key takeaways

I started with a C loop and one idea: handle more than a byte per iteration. Looking at the pipeline first is what gave me a real way to judge what to try next in assembly. Unrolling can separate dependent instructions and cut down on loop bookkeeping, but whether that turns into a measurable speedup still depends on the core, the alignment of the data, the memory system, and what the compiler was already doing before I got involved.

That is what stayed with me after the interview. Computer architecture turned a list of performance tricks into questions I could actually answer from first principles, instead of habits I was just applying by feel.
