Introduction

Cache replacement and prefetching policies are usually designed independently, despite strongly interacting with one another. PACIPV (Prefetch-Aware Coarse-grained Insertion and Promotion Vectors), introduced by Mostofi et al. at ISCA 2025, is a lightweight policy that generalizes SRRIP by using structured insertion/promotion vectors to better distinguish blocks with differing locality characteristics. For our CSCE 614 term project we implemented PACIPV, a novel policy not available in ZSim, and evaluated it against seven established baselines using SPEC CPU2006 and PARSEC benchmarks. Because ZSim's prefetch path could not be made stable in our environment, our implementation runs in demand-only mode, so it evaluates the intrinsic insertion/promotion logic of PACIPV rather than its full prefetch-aware design.

Policies implemented

Three replacement policies were implemented from scratch in ZSim (PACIPV, DRRIP, SHiP); the remaining baselines (LRU, LFU, NRU, Rand, TreeLRU, SRRIP) were already available or provided as reference implementations.

PACIPV (new policy)

PACIPV generalizes SRRIP's fixed insertion/promotion rule using an Insertion and Promotion Vector (IPV). Each cache line carries a 2-bit Re-Reference Prediction Value (RRPV). SRRIP corresponds to a fixed vector V = [0,0,0,0,2] (always insert at RRPV = 2, always promote hits to 0). PACIPV without prefetching instead uses V = [0,1,1,0,3]: the last entry (3) is the insertion RRPV for a new miss, and the first four entries map a block's current RRPV to its updated RRPV on a hit (e.g. a hit on RRPV = 2 updates it to V[2] = 1). The original design uses separate IPVs for demand and prefetch accesses; our version uses only the demand-access IPV, since ZSim's prefetch path could not be wired in reliably.

DRRIP

DRRIP dynamically chooses between SRRIP-style insertion (good scan resistance) and BRRIP-style insertion (good thrash resistance) using set-dueling: dedicated SRRIP and BRRIP leader sets are assigned modulo-style (e.g. every 32nd set), a saturating PSEL counter tracks which leader set is missing less, and follower sets pick their insertion policy from PSEL's value.

SHiP

SHiP predicts reuse per access stream signature rather than treating all misses identically. A Signature History Counter Table (SHCT) is incremented when a line with a given signature is hit and decremented if it is evicted without ever being reused; the counter then decides whether new lines from that signature insert near (likely reused) or far (likely dead-on-arrival). Since ZSim exposes no program counter, we approximate signatures with region-based address hashing combined with core ID.

Implementation details

Files modified: pacipv_repl.h, drrip_repl.h, ship_repl.h, init.cpp, and the replacement-policy config files. Each policy is implemented as a class inheriting from ZSim's ReplPolicy and overriding three functions: candidate ranking (victim selection), update (called on a hit), and replaced (called on a miss/insertion).

Step-by-step: PACIPV

01Initrrpv_array set to rpvMax for all lines
→
02Hitrrpv_array[line] = pacipv_array[current RRPV]
→
03MissInsert at pacipv_array[rpvMax + 1] (= 3)
→
04EvictrankCands finds RRPV == rpvMax, aging set if none found

Invalid (empty) lines are always evicted first, regardless of RRPV. If no line currently has RRPV = rpvMax, every line in the set is aged (RRPV incremented) until at least one does.

PACIPV victim selection · simplifiedC++
int rankCands(const Set& set, int rpvMax) {
    // Invalid lines are evicted immediately
    for (int way = 0; way < set.ways(); ++way)
        if (!set[way].valid()) return way;

    // Find a line at maximum RRPV
    while (true) {
        for (int way = 0; way < set.ways(); ++way)
            if (rrpv_array[way] == rpvMax) return way;
        // Age every line in the set until one reaches rpvMax
        for (int way = 0; way < set.ways(); ++way)
            rrpv_array[way]++;
    }
}

void update(int way) {                 // on hit
    int r = rrpv_array[way];
    rrpv_array[way] = pacipv_array[r];  // V = [0,1,1,0,3]
}

void replaced(int way, int rpvMax) {   // on miss / insertion
    rrpv_array[way] = pacipv_array[rpvMax + 1]; // insertion RRPV = 3
}

Step-by-step: DRRIP

01Classify setSRRIP leader / BRRIP leader / follower
→
02InsertSRRIP: rpvMax−1 · BRRIP: rpvMax−1 (31/32) or rpvMax (1/32)
→
03Update PSELLeader-set miss increments (SRRIP) or decrements (BRRIP)
→
04Follower decisionPSEL below threshold → SRRIP; else → BRRIP

On a hit, RRPV is always reset to 0. Victim selection ages the set the same way as PACIPV/SRRIP: evict the line at rpvMax, aging everyone if none currently qualifies.

Step-by-step: SHiP

01SignatureRegion-hashed address + core ID (no PC in ZSim)
→
02MissSHCT counter == 0 → insert at rpvMax; else insert at rpvMax−1
→
03HitRRPV → 0; if first hit for the line, increment SHCT and set outcome bit
→
04Eviction / trainingIf line's outcome bit is unset, decrement its signature's SHCT counter

This closed feedback loop lets SHCT counters drift toward the true reuse behavior of each signature over the run, even with the coarser, PC-free signatures forced by ZSim's constraints.

Evaluation methodology

Benchmarks

SPEC

bzip2, calculix, cactusADM, gcc, hmmer, lbm, libquantum, mcf, namd, sjeng, soplex, xalan, single-core.

PARSEC

blackscholes, bodytrack, canneal, fluidanimate, streamcluster, swaptions, x264, 8-core, simlarge.

Metrics

  • IPC = Total Instructions Retired / Total Cycles (per-core geometric mean).
  • MPKI = LLC Misses / Instructions Retired × 1000 (arithmetic mean across active cores).
  • Total cycles = max across cores for PARSEC (multithreaded), sum of cycles for SPEC (single-core).
  • Weighted Speedup = Σ (IPCpolicy / IPCLRU) across benchmarks, i.e. performance relative to the LRU baseline.

CSV summaries and IPC / MPKI / Weighted-Speedup bar plots were generated per benchmark suite to support cross-policy comparison.

Results

SPEC's structured access patterns produced a narrow MPKI band (~14–15) across all nine policies, so IPC varied only slightly. PARSEC's multithreaded workloads showed much lower MPKI (~2–3), reflecting greater locality and inter-thread sharing. Across both suites, performance closely tracked MPKI: LFU had the lowest MPKI and highest IPC/speedup overall, while DRRIP and SHiP led among the RRIP family, especially on PARSEC. PACIPV tracked SRRIP and LRU closely on both suites, finishing 0.43% below LRU's geometric-mean IPC on SPEC and 0.09% below on PARSEC.

Analysis & limitations

Why PACIPV tracked SRRIP so closely

Under demand-only operation, PACIPV's coarse-grained IPV behaves very similarly to SRRIP's fixed insertion/promotion rule, since the workloads tested didn't stress the distinctions the vector was designed to make. The original paper's larger gains depend on the prefetch-aware, dual-IPV design, which we could not exercise here.

Implementation constraints

  • Enabling ZSim's L3 prefetch path triggered persistent assertion failures, forcing PACIPV into a demand-only variant with prefetch-aware IPVs disabled.
  • ZSim exposes no program counter, so SHiP's signatures were approximated via region-hashed addresses + core ID instead of true PC-based classification, reducing SHCT resolution.
  • Both PACIPV and SHiP trained exclusively on demand GETS/GETX requests, since prefetch metadata could not be processed reliably.
  • Replacement-policy state was spread across several structures (RRPV arrays, IPV tables, SHCT), so small bugs in signature assignment or RRPV updates produced outsized swings in MPKI/IPC and required careful tracing to debug.
  • Full-length simulation runs were slow, so many bugs surfaced only after complete runs, slowing iteration on policy tuning.

Conclusion

SRRIP served as a stable baseline; DRRIP added limited adaptability via set-dueling; SHiP extended that adaptability through signature-based learning; and PACIPV aimed to refine insertion decisions using its coarse-grained vector. All three RRIP-family extensions performed close to LRU/SRRIP under our demand-only, PC-free ZSim environment: the practical constraints of the simulator, more than the policies' designs, limited how far PACIPV and SHiP could differentiate themselves from the baselines. Evaluating the full prefetch-aware PACIPV design remains a promising direction for future work.
