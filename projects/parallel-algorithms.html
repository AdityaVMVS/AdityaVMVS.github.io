Introduction

Adding threads does not automatically make a program faster. Small inputs can spend more time creating workers and waiting at barriers than doing useful computation. Larger inputs provide more work per worker, but eventually encounter limits from synchronization, scheduling, memory traffic, and the serial portions of the program.

I investigated these tradeoffs through CSCE 735 coursework. I benchmarked supplied pthreads and MPI programs for estimating π, implemented a pthread-based parallel merge sort, and compared execution time, speedup, and efficiency across workload sizes and worker counts. The next stage applies OpenMP to recursive matrix multiplication.

03

Project details

The project progresses from running controlled benchmarks to implementing synchronization in a parallel algorithm. Each stage asks where additional workers help and where their overhead begins to outweigh the benefit.

3.1 Establish shared-memory scaling behavior

I began by compiling and benchmarking the supplied pthreads program for estimating π. Holding the problem size fixed while increasing the number of threads makes this a strong-scaling experiment. Each configuration was evaluated using runtime, speedup, and efficiency.

Performance definitionsAnalysis
Speedup S(p) = T(1) / T(p)
Efficiency E(p) = S(p) / p

T(1): elapsed time with one worker
T(p): elapsed time with p workers

What was observed: The HW1 report records a minimum runtime of 0.0258 s at 128 threads for 108 trials, and 2.2166 s at 512 threads for 1010 trials. In the larger case, runtime increased to 2.3616 s at 8192 threads.

The larger problem benefited from more workers before overhead dominated. These are the best measured configurations in this experiment, not universal optimal thread counts. A thread count also does not imply an equal number of physical cores.

3.2 Evaluate distributed-memory execution with MPI

I benchmarked the supplied MPI numerical integration program, first varying the number of ranks and then changing process placement while holding the total rank count fixed. This separates the question of how much parallelism to use from how to distribute that parallelism across nodes.

  1. Scale the rank count

    For 108 intervals, compare configurations through 64 MPI processes with four tasks per node.

  2. Change process placement

    For 1010 intervals and 64 total processes, vary tasks per node and compare total execution time.

  3. Track numerical accuracy

    Study the relative error as problem size changes, alongside runtime and speedup.

What was observed: The report records 0.04658476 s at 64 processes for the 108-interval experiment. For 1010 intervals and 64 processes, the minimum reported total time was 0.26692614 s at 16 tasks per node, corresponding to four nodes.

The pthreads and MPI programs use different numerical methods. Their raw runtimes should not be interpreted as a direct comparison of pthreads versus MPI. Scaling is evaluated against each program's own baseline.

3.3 Implement parallel merge sort with pthreads

The sorting program divides an input of 2k integers across 2q threads. Each worker first sorts its own contiguous sublist with qsort(). Workers then cooperate through successive merge levels until the complete list is sorted.

  1. Sort local partitions

    Each thread obtains its identifier through thread-local storage and sorts its assigned region. A barrier ensures every local sublist is ready before merging begins.

  2. Compute merge destinations

    Workers find the position of their first value in the partner block with binary search, then advance through the sorted partner block for later values. Strict and non-strict comparisons distinguish equal values from opposite blocks.

  3. Separate write and copy phases

    Threads scatter values into a shared work array. One barrier waits for all writes; each thread then copies its assigned range back, and a second barrier prevents the next level from reading a partially updated list.

  4. Check against a reference

    The program sorts a copy of the original input with qsort() and compares every output element. It deliberately repeats one value to exercise duplicate handling.

Synchronization at each merge level · excerptC
// All workers finish scattering before copying begins.
pthread_barrier_wait(&barrier);
for (i = ptr[my_id]; i < ptr[my_id + 1]; i++) {
    list[i] = work[i];
}
// All copies finish before the next merge level.
pthread_barrier_wait(&barrier);

Timing scope: The supplied implementation times thread creation, parallel sorting, and thread joins. Initialization and the reference qsort() check are outside that timed interval. Reported speedup uses the one-thread execution of this implementation.

3.4 Extend to OpenMP matrix multiplication

Current status: ongoing. HW3 starts from a serial C++ implementation of Strassen's algorithm. It recursively computes seven submatrix products and switches to conventional multiplication at a configurable leaf size. The uploaded source includes OpenMP timing, but no #pragma omp directives, so no completed OpenMP scaling result is claimed here.

The planned implementation will expose independent recursive products as parallel work, synchronize before combining their results, and limit task creation for small subproblems. The evaluation will vary leaf size and compare parallel execution with single-thread Strassen execution using the same matrix and cutoff.

Before collecting results, the timing variable should use double to preserve the precision of omp_get_wtime(). Correctness checks should also cover larger cases: the current baseline only compares against conventional multiplication when k < 11.

3.5 What the experiments establish

  • Correct synchronization is necessary before scaling measurements are meaningful.
  • Larger inputs can amortize thread-management and synchronization costs.
  • The fastest configuration and the most efficient configuration are different objectives.
  • Process placement affects measured MPI runtime even when the total rank count is fixed.
  • Timing trends suggest possible bottlenecks; profiling is needed to isolate their causes.

Results & takeaways

The HW2 report shows a clear relationship between input size and useful parallelism. For 220 integers, the best tested configuration was 64 threads. For 228 integers, it was 256 threads.

13.88× speedup

1,048,576 integers: 0.1402 s with one thread, reduced to 0.0101 s with 64 threads.

28.43× speedup

268,435,456 integers: 49.8663 s with one thread, reduced to 1.7543 s with 256 threads.

83.5% efficiency

The largest input achieved about 83.5% parallel efficiency at 16 threads, versus 11.1% at its fastest 256-thread configuration.

Diminishing returns

At 1024 threads, the largest-input runtime rose to 2.1018 s. More threads did not improve the best measured time.

Implementation & next steps

The completed work includes the pthread merge-sort implementation and the HW1/HW2 benchmark reports. Upcoming work covers OpenMP parallelization, further MPI development, and CUDA GPU acceleration. Follow the project in the Parallel-Algorithms GitHub repository linked below.

Next experiments

  • Complete and validate OpenMP Strassen parallelization, then tune task granularity and leaf size.
  • Repeat benchmarks and report timing variability along with speedup and efficiency.
  • Extend MPI work with an implemented distributed workload and measure communication time separately from computation.
  • Explore a CUDA matrix-multiplication version and include host/device transfer costs in end-to-end timing.

The big picture: OpenMP, MPI, and CUDA together

The final goal is to run and manage a parallel workload across a complete system: use MPI to coordinate work between nodes, OpenMP to parallelize CPU work within each node, and CUDA to accelerate suitable computation on GPUs. This stage will bring together resource allocation, workload placement, synchronization, and data movement, with correctness checks and end-to-end performance measurements.

Target completion: the first week of December 2026. Implementation updates and results will be added as the OpenMP, MPI, and CUDA stages progress. Stay tuned!
