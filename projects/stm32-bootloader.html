STM32 Firmware Bootloader with Fail-Safe Updates

The board keeps its working firmware while it tries an update. If the new firmware gets stuck, the bootloader can bring the old version back.

BoardNUCLEO-F767ZI
Update linkUSART3 at 115200 baud
Flash layoutTwo application slots
Trial limitThree boot attempts

Why I chose this project

I wanted to see what happens when a firmware update goes wrong. A cable can come loose halfway through a transfer, and a firmware file can arrive intact but still hang on startup. I used those two situations to decide what the bootloader should do before and after resetting the board.

Send an image→Check it in flash→Try to boot→Confirm or roll back

The bootloader and LED demos are written in C. Python packages the binary and sends it over the ST-LINK USB connection. I used the Arm GNU Toolchain for builds and documented first-time programming over SWD with STM32CubeProgrammer.

How I split up flash

The STM32F767ZI has 2 MiB of internal flash. I used single-bank mode and divided it along the chip’s erase-sector boundaries. Each application slot gets three 256 KiB sectors. Updating B can then erase all three of its sectors while A stays available.

  • Bootloader. The first 128 KiB starts at 0x08000000.
  • Primary boot journal. The next 128 KiB starts at 0x08020000.
  • Slot A and slot B. They start at 0x08040000 and 0x08100000.
  • Backup boot journal. The last 256 KiB starts at 0x081C0000.

A 512-byte header sits at the front of each slot. The vector tables start at 0x08040200 and 0x08100200, so the same source builds into two binaries at different addresses. Flash operations can stall the processor in single-bank mode. The bootloader does the update before handing control to an application, and the host waits for each reply before sending more data.

Sending an update

The Python tool adds a header with the target ID, firmware version, length and SHA-256 digest. It sends that package over USART3 through the Nucleo’s virtual COM port on PD8 and PD9. Every packet carries a sequence number and a CRC32. If an acknowledgment is lost, Python sends the same packet again and the bootloader replays the reply.

The bootloader only writes to the selected inactive slot. Once the transfer finishes, it checks the header CRC, validates the application stack and reset addresses, and calculates the SHA-256 digest from flash. Only then does it make the image pending. A transfer cut short can be started over from the beginning. The current design detects corruption and accepts unsigned packages from a trusted host.

What happens on the next boot

The boot journal records which image was confirmed, which is pending and how many attempts the pending image has had. The bootloader writes a CRC and a final commit marker for each record. If a reset interrupts the write, the next boot can use the previous valid record. When one journal sector fills, the next record goes into the other sector.

Before starting the pending application, the bootloader saves the attempt count and starts the independent watchdog. It then points the Cortex-M7 at the application’s vector table, loads its stack pointer and jumps to its reset handler. The healthy LED demo confirms itself after startup. The failing demo hangs on purpose. If B uses all three tries, the bootloader returns to A when A is still valid. With no usable application, it waits for a serial update. Holding the user button during reset also opens recovery.

What I checked

The bootloader and three demo binaries build with the Arm toolchain. The Python tests check packaging, bad frames and retries. The C tests run the journal and image checks against simulated flash, including a write that stops before the journal commit finishes.

Board testing is still pending. I want to confirm the watchdog rollback on the Nucleo, interrupt updates during erase and programming, and measure startup, transfer and recovery times. The next application milestone is a FreeRTOS demo that waits for its critical tasks to report healthy before confirming the update.
