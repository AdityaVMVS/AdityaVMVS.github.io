Introduction

This project explores hardware/software partitioning on a Zynq SoC. A custom AXI4-Lite peripheral runs in the FPGA fabric, while the dual-core ARM Cortex-A9 processing system runs embedded Linux. A memory-mapped register interface provides a small and predictable contract between both domains.

The hardware is exposed through a kernel module and character device, allowing a normal userspace program to configure the accelerator, submit data, and read results without knowing the physical register addresses. The design demonstrates the full stack: RTL, AXI integration, device tree, kernel driver, and application-level validation.

Project details

The project begins by defining a small register map that acts as the contract between software and hardware. Keeping this interface narrow makes each layer easier to test independently and avoids coupling the Linux application to the accelerator implementation.

Implementation outline

  1. Define the hardware/software contract

    Choose control, status, input, and output registers; document offsets, widths, reset values, and access permissions.

  2. Implement the custom AXI4-Lite peripheral

    Create the RTL datapath and register interface, then validate address decoding and read/write responses in simulation.

  3. Integrate the Zynq block design

    Connect the custom IP to the processing system through AXI interconnect, assign an address range, and generate the bitstream.

  4. Build the embedded Linux platform

    Import the hardware description into PetaLinux, configure boot components, and add the peripheral node to the device tree.

  5. Develop the kernel driver

    Map the register region, register a character device, and provide controlled read/write operations to userspace.

  6. Validate end-to-end behavior

    Run known input vectors, compare hardware results against a software reference, and measure transaction latency.

Register-level communication

The kernel driver maps the physical AXI address range once during probe. All later accesses use Linux I/O helpers so reads and writes preserve the correct device-memory semantics.

Kernel driver · register accessC
#define REG_CONTROL 0x00
#define REG_INPUT   0x04
#define REG_OUTPUT  0x08

iowrite32(input_value, regs + REG_INPUT);
iowrite32(0x1, regs + REG_CONTROL);
result = ioread32(regs + REG_OUTPUT);

The driver uses the kernel I/O helpers instead of directly dereferencing mapped addresses. This preserves the required memory-access semantics when communicating with the AXI peripheral.

Why a character driver?

It provides a familiar file-based interface, isolates privileged register access inside the kernel, and gives the application a clean API that can evolve independently of the RTL register map.

Userspace interface

Userspace · character deviceC
int fd = open("/dev/zynq_accel", O_RDWR);
write(fd, &input, sizeof(input));
read(fd, &result, sizeof(result));
close(fd);

The application interacts with a normal device file. Hardware addresses and synchronization remain encapsulated inside the driver, keeping the userspace interface small and portable.

Validation checklist

  • Verify register reset values before the first transaction.
  • Test boundary values and invalid control combinations.
  • Compare FPGA output with a known-good software implementation.
  • Capture AXI transactions with an Integrated Logic Analyzer when debugging.
  • Measure repeated transfers to identify software and hardware latency.
