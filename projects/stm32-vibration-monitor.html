Real-Time Vibration Analysis and Fault Detection on STM32

An accelerometer measures how a motor vibrates. The STM32 learns its usual pattern and raises an alert when that pattern changes for several windows in a row.

BoardNUCLEO-F767ZI
SensorGY-291 ADXL345
Nominal sample rate1,600 samples/s per axis
Analysis window1,024 samples

Why I chose this project

I wanted to see what a small accelerometer could tell me about a motor. A fan might start shaking harder, or the main frequency might move when its operating conditions change. I wanted the STM32 to spot those changes as it collected the data, with the laptop there to show what happened.

Read the sensor FIFO→Filter and run the FFT→Compare with the baseline→Send the result

Getting samples off the sensor

The GY-291 breakout is meant to sit firmly on the stationary motor housing. I configured the ADXL345 for 1600 samples per second on X, Y and Z, in full-resolution mode with a ±8 g range. The Nucleo reads it over four-wire SPI at 4 MHz. I used PB5 for MOSI and PB1 for the interrupt to avoid pins shared with Ethernet and the green LED.

The sensor collects readings in a FIFO and raises an interrupt at 16 samples, about every 10 ms. That wakes the highest-priority FreeRTOS task. It uses DMA to read one X/Y/Z set per SPI transaction, then fills a fixed-size buffer. Analysis works on completed windows while acquisition keeps taking samples. The DMA transfer arrays sit in SRAM1 so DMA2 can access them.

Turning motion into useful numbers

Each window covers 640 ms and overlaps the previous one by half, so the firmware can report about every 320 ms. It processes one selected axis. It removes the average and uses a 10 Hz high-pass filter to reduce slow changes. From this signal it calculates RMS, peak, crest factor and kurtosis.

A Hann window smooths the ends of the samples before the CMSIS-DSP FFT. The FFT separates the movement into frequencies, with bins about 1.56 Hz apart. I use the spectrum to find the strongest frequency, its energy and centroid, and how the energy is spread across 10–100 Hz, 100–300 Hz and 300–600 Hz.

Learning what normal looks like

The first 64 windows teach the firmware what to expect for RMS, dominant frequency, spectral energy and kurtosis. After that, it measures how far each new window falls from the baseline. A sustained rise in vibration can trigger a warning or a critical alert. A frequency shift or a change in the shape of the signal can trigger an anomaly.

The detector waits for three unusual windows so a single bump does not leave an alert on. It reports sensor and acquisition failures separately, and starts a fresh window after a data gap. This is condition monitoring. Using the signal to estimate when a motor will fail would need longer-term measurements from machines tracked through failure.

Dashboard and testing

The board sends feature values, the condition, error counts and timing over the ST-LINK virtual serial port. The Python dashboard logs them to CSV and plots changes in RMS and band energy. I can also request a raw three-axis window to plot its spectrum on the laptop and compare it with the STM32’s output.

The Arm firmware builds, and 42 automated tests passed on the host. The tests compare the firmware’s C analysis code with SciPy using known tones, noise and other synthetic signals. They also check when alerts turn on and off and how the serial parser handles missing or damaged data. Sensor bring-up, real motor measurements and the 24-hour test still need to run on the board.
